# 21. Wissensquellen kontrolliert einarbeiten

Der gleiche Grundgedanke funktioniert nicht nur für Sourcecode.

Auch größere Dokumentationsquellen sollten nicht einfach vollständig in den Context gekippt und in einem Rutsch „zusammengefasst“ werden.

## Drei Phasen

Ich trenne solche Arbeiten gern in:

```text
Source Intake
→ Quelle aufnehmen und strukturieren

Topic Synthesis
→ genau ein Thema aus relevanten Quellen bearbeiten

Source Finalization
→ erfolgreiche Verarbeitung dokumentieren und Quelle abschließen
```

Das Template enthält dafür neutrale Workflow-Beispiele.

## Quelle aufnehmen

Zuerst werden Metadaten und Struktur ermittelt.

Ein Skript kann beispielsweise Seiten, Abschnitte oder Dateitypen erfassen.

Das Modell bekommt nur die Information, die es für die Planung der Verarbeitung braucht.

## Ein Thema statt eine ganze Sammlung

Danach wird nicht „alles“ gleichzeitig verarbeitet.

Für ein Thema werden gezielt die relevanten Abschnitte geladen.

Das reduziert Context und macht Widersprüche sichtbar.

## Widersprüche bleiben Widersprüche

Wenn zwei Quellen unterschiedliche Aussagen enthalten, entscheidet das Modell nicht selbst, welche davon angenehmer klingt.

Der Konflikt wird dokumentiert.

Das ist derselbe Grundsatz wie beim Architekturwissen:

```text
Unknown bleibt Unknown.
Conflict bleibt Conflict.
```

## Finalisierung erst am Ende

Eine Quelle wird erst dann als verarbeitet markiert oder archiviert, wenn der entsprechende Verarbeitungsschritt wirklich abgeschlossen ist.

Damit ist auch dieser Dokumentationsworkflow nachvollziehbar und wiederaufnehmbar.
